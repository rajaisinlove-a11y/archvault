You are the senior engineer and lead developer for this project. Build a production-quality, client-specific cloud storage application that works on Android, Linux, Windows, and macOS.

The product should feel like a modern cloud drive, taking UX inspiration from Google Drive, Dropbox, TeraBox, Teldrive, and dDrive. Do not copy their source code or branding. Study their publicly available implementations and UX patterns where useful, respect licenses, and implement our own system.

## Core storage requirement

Internet Archive IAS3/S3-compatible storage is the primary object-storage backend.

The application must support:

* Upload files

* Multiple downloads
* Folders

* Delete

## Critical memory requirement

This application must run on very weak hardware, including machines with approximately 2–3 GB RAM.

Do not load entire files into RAM.

Do not create an architecture where a 10 GB file becomes a 10 GB byte array/blob.

All large-file operations must be streaming and bounded.

Use bounded buffers and backpressure.

Memory consumption must remain approximately independent of file size.

## Chunking requirement

Every large transfer must use logical chunks no larger than:

50 MiB = 52,428,800 bytes.

Define this as a single constant.

Never create an implementation where 50 MiB is multiplied by an uncontrolled number of simultaneous workers.

The actual streaming buffer can be substantially smaller than the logical chunk size.

Test these boundaries:

* 1 byte
* 1 MiB
* 49 MiB
* 50 MiB
* 50 MiB + 1 byte
* 100 MiB
* 500 MiB
* 1 GiB

Verify that:

sum of chunk sizes = original file size

and:

every chunk <= 50 MiB.

## Upload system

Implement a dedicated transfer subsystem rather than putting transfer logic into UI components.

Uploads must:

* Stream from disk
* Use bounded memory
* Report progress
* Support cancellation
* Retry appropriate transient errors
* Persist transfer state
* Recover from application interruption where possible
* Verify integrity
* Avoid loading the entire file into memory

Multiple files must use bounded concurrency.

Do NOT simply create one worker per selected file.

The queue must be bounded.

## Download system

Downloads must:

* Stream from IAS3
* Write incrementally to disk
* Avoid whole-file RAM allocation
* Support range/chunked retrieval where IAS3 permits it
* Support cancellation
* Support retries
* Preserve partially downloaded data when possible
* Resume interrupted transfers where possible
* Verify integrity
* Use temporary `.part` files
* Atomically finalize completed files

Never expose an incomplete download as a completed file.

## Transfer state

Create an explicit transfer state machine.

Possible states include:

QUEUED
PREPARING
TRANSFERRING
PAUSED
VERIFYING
COMPLETED
FAILED
CANCELLED
RETRYING

Persist important transfer information locally so the application can recover after restart.

Do not rely solely on UI state.

## Integrity

Use incremental hashing.

Do not read an entire file into RAM merely to calculate SHA-256.

The system must be capable of comparing:

original SHA-256

against:

downloaded SHA-256.

## Retry behavior

Implement bounded retries with exponential backoff and jitter.

Differentiate transient errors from permanent errors.

Do not endlessly retry:

* invalid credentials
* permission failures
* invalid requests
* missing objects
* user cancellation
