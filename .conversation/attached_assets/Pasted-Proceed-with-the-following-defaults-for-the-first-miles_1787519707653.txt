Proceed with the following defaults for the first milestone:

1. **Authentication:** Single-user/local-account only for the first version. Do not implement multi-user accounts, collaboration, or shared storage yet. Keep the architecture extensible so multi-account support can be added later.

2. **IAS3 storage model:** Use one configured Internet Archive item per account, with object keys representing the logical folder/file hierarchy. Files should remain private to the configured account for now. Do not implement sharing or public-link generation in the first milestone.

3. **Target/platform priority:** Desktop-first with responsive Android UI is acceptable for the first milestone. Native Android background transfers, foreground-service integration, scoped-storage handling, and lifecycle recovery should be implemented as a dedicated follow-up phase rather than faked in the initial UI.

4. **Important implementation requirements:**

   * Do not use fake files, fake transfers, fake progress, or simulated backend results.
   * Any operation not actually connected to IAS3 must display an explicit unavailable/under-development state.
   * Keep IAS3-specific behavior strictly inside the storage-provider adapter.
   * Keep transfer scheduling, hashing, retries, cancellation, persistence, and filesystem operations outside React components.
   * Never store credentials in source code, Git history, frontend bundles, logs, or generated configuration files. Load them only from Replit Secrets/runtime configuration.
   * Use `MAX_LOGICAL_CHUNK_SIZE = 52,428,800` bytes as the shared logical chunk limit, while keeping actual memory buffers significantly smaller.
   * Do not load entire files into memory for upload, download, hashing, previewing, or verification.
   * Use stable IDs for files/folders and preserve hierarchy consistently across navigation, transfers, and local persistence.
   * Persist transfer state in SQLite so interrupted transfers can recover cleanly.
   * Partial downloads must remain `.part` files and must never be presented as completed files.
   * The Transfer Center must consume real typed engine events and must not independently invent percentage, speed, ETA, or completion state.
   * Backend capability limitations must be represented explicitly rather than hidden behind optimistic UI.

5. **First milestone scope:**
   Build the complete application shell and responsive file-browser experience first, including navigation, breadcrumbs, folder hierarchy, selection, search interface, context menus, details, preview states, and the transfer-center UI contract. Then wire the real IAS3 provider and transfer engine incrementally.

6. **Validation standard:**
   Do not mark a feature as complete merely because the UI exists. A feature is complete only after its underlying provider/engine behavior is implemented and tested against real operations. Keep clear separation between:

   * implemented and tested
   * implemented but unavailable for the current backend
   * UI-only / under development

Please proceed with these decisions and keep the architecture provider-agnostic so another S3-compatible backend can be added later without rewriting the UI or transfer engine.
